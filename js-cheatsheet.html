Standard-Grundgerüst (Vorlage für jede Aufgabe)

Wann: Immer als Startpunkt. Das Script steht im <head>, wird also ausgeführt, bevor die Elemente im <body> existieren – darum wartet man auf DOMContentLoaded.

<!DOCTYPE html>
<html lang="de">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Titel</title>
  <link rel="stylesheet" href="style.css">
  <script src="script.js"></script>      <!-- externes Script (im head → DOMContentLoaded nötig) -->
</head>
<body>
  <h1 id="titel">Hallo</h1>
  <button id="btn">Klick mich</button>
</body>
</html>
// script.js
document.addEventListener("DOMContentLoaded", () => {
  // Ab hier existiert das ganze HTML → Elemente dürfen gesucht werden
  const btn = document.querySelector("#btn");
  btn.addEventListener("click", () => {
    document.querySelector("#titel").textContent = "Geklickt!";
  });
});
Alternativen zu DOMContentLoaded: <script src="script.js" defer></script> im head, oder das <script> ganz unten vor </body>.

JavaScript einbinden

Wann: Inline nur für Mini-Tests; sonst externe Datei (sauber, wiederverwendbar, cachebar).

<!-- 1) Inline im HTML -->
<script>
  alert("Hallo");
</script>

<!-- 2) Extern (Datei script.js, im selben Ordner) -->
<script src="script.js"></script>

<!-- 3) Extern, lädt parallel, läuft nach dem HTML-Parsen -->
<script src="script.js" defer></script>

<!-- 4) Als ES-Modul (import/export möglich, ist automatisch defer) -->
<script type="module" src="main.js"></script>

<!-- 5) Inline-Handler im HTML-Attribut (veraltet, vermeiden) -->
<button onclick="alert('Hi')">Klick</button>
Ein <script src="…"> darf keinen Code zwischen den Tags haben – der wird ignoriert. <script> ist nie selbstschliessend (<script … /> ✘) und <link> ist nur für CSS.
Inline-JavaScript = JS im HTML-Attribut (onclick="…"). Nur für Mini-Beispiele; bei vielen/mehrzeiligen Anweisungen unübersichtlich → externe Datei. JS wird vom Browser (JS-Engine) ausgeführt, nicht vom Betriebssystem.

// Lösung: warten

  • console.log(btn) – ist es null?

Probeprüfung & Prüfungs-Taktik

Alle 12 Fragen der Probeprüfung mit richtiger Antwort und Begründung – die Prüfung fragt dieselben Muster in Varianten ab. Die Quellcode-Vorlagen der Fragen fehlten; die HTML-Struktur unten ist aus den Antworten rekonstruiert.

Taktik bei Multiple-Choice (mehrere Antworten richtig)

  • Die Fragen sind meist «Mehrfachauswahl»: oft sind 2–3 Antworten richtig. Jede Antwort einzeln prüfen, nicht bei der ersten richtigen aufhören (in der Probe gab es bei Frage 2, 3, 4, 5, 7 Teilpunkte, weil nur ein Teil erkannt wurde).
  • Punkte = Anteil der gefundenen richtigen Antworten (2 von 3 → 0.67, 1 von 2 → 0.5, 1 von 3 → 0.33). Ob falsche Auswahl zusätzlich Abzug gibt, ist aus der Probe nicht ersichtlich (Frage 6 = 0 Punkte: nur falsche Antworten gewählt) → im Zweifel nichts raten, aber alle sicheren ankreuzen.
  • Prüfen, was alle / jedes / erste / letzte heisst: «aus jeder Liste das erste» ≠ «das allererste li der Seite».
  • Erfundene Methoden erkennen (siehe «Was gibt es NICHT?» im Abschnitt DOM): addChild, addClass, removeAll, getElementByClassName … → sofort falsch.
  • Klein-/Grossschreibung und Mehrzahl beachten: getElementsBy… (Mehrzahl), getElementById (Einzahl), innerHTML, classList.
  • Selektor-Syntax: # ID, . Klasse; bei getElementById ohne #, bei querySelector mit.
  • Frage mit «Quellcode»: HTML-Struktur zuerst genau anschauen (welche Elemente, welche Klassen/IDs, Nachbarn, Verschachtelung).
  • Textfragen (z.B. «Beschreiben Sie …»): in ganzen Sätzen antworten – Definition, Einsatzsituation, Interaktion = 3 Teile bei 2 Punkten. Musterantworten siehe unten und im Abschnitt «Konzepte».

Frage 1 – JavaScript im Browser

Richtig:

  • ✔ Im Gegensatz zu HTML und CSS kann mit JS programmiert werden (Variablen, Schleifen, Bedingungen, Funktionen). HTML = Auszeichnung/Struktur, CSS = Gestaltung.
  • ✔ Inline-JavaScript = JS innerhalb eines HTML-Attributs, z.B. <button onclick="alert('Hi')">.
  • ✔ JS wird vom Browser ausgeführt (JavaScript-Engine, z.B. V8).

Falsch:

  • ✘ «vom Betriebssystem ausgeführt» – nein, vom Browser (Node.js wäre die Ausnahme ausserhalb des Browsers).
  • ✘ «viele mehrzeilige Inline-Anweisungen bleiben übersichtlich» – im Gegenteil: unübersichtlich, nicht wiederverwendbar → externe .js-Datei + addEventListener.

Frage 2 – Wie ist der DOM beim Ausführen schon geladen?

3 richtige Varianten:

<!-- 1) BESTE Variante: defer -->
<script src="script.js" defer></script>

<!-- 2) Script ganz am Ende des body -->
<body> … <script src="script.js"></script> </body>

<!-- 3) Klassisch: im head + auf das Ereignis warten -->
<script src="script.js"></script>
<script>document.addEventListener("DOMContentLoaded", () => { /* … */ });</script>

Falsch:

  • ✘ <link rel="javascript" href="…" defer /> – <link> ist für CSS; JS braucht <script>.
  • ✘ <script src="…" defer /> – <script> darf nicht selbstschliessend sein, es braucht </script>.
defer lädt das Script parallel und führt es aus, sobald das HTML fertig geparst ist (Reihenfolge bleibt erhalten). async führt sofort nach dem Laden aus (Reihenfolge nicht garantiert) – nicht für DOM-Scripts.

Frage 12 – Modaler Dialog beschreiben (Musterantwort für 2 Punkte)

Musterantwort: Ein modaler Dialog ist ein Fenster bzw. Overlay, das über der eigentlichen Seite erscheint und diese blockiert: Der Benutzer muss den Dialog zuerst bearbeiten (bestätigen, abbrechen, schliessen), bevor er mit der restlichen Seite weiterarbeiten kann; der Hintergrund ist meist abgedunkelt und nicht klickbar. Er wird verwendet, wenn eine wichtige Entscheidung oder Eingabe nötig ist, z.B. eine Sicherheitsabfrage vor dem Löschen («Wirklich löschen?»), ein Login-Formular, eine Cookie-Einwilligung oder das Anzeigen von Details/Hilfe. Der Benutzer interagiert mit Schaltflächen wie «OK»/«Abbrechen», einem «×» oder der Escape-Taste; danach verschwindet der Dialog und die Seite ist wieder bedienbar. Im Unterschied dazu blockiert ein nicht-modaler Dialog (z.B. Tooltip, Chat-Fenster) die Seite nicht.

Umsetzung mit dem HTML-Element <dialog> (siehe auch Abschnitt «Konzepte»):

<dialog id="dlg">
  <p>Eintrag wirklich löschen?</p>
  <form method="dialog">                    <!-- schliesst den Dialog automatisch -->
    <button value="abbrechen">Abbrechen</button>
    <button value="ok">Löschen</button>
  </form>
</dialog>
<button id="open">Löschen …</button>
const dlg = document.querySelector("#dlg");
document.querySelector("#open").addEventListener("click", () => dlg.showModal());   // modal (blockiert Seite, Esc schliesst)
dlg.addEventListener("close", () => {
  if (dlg.returnValue === "ok") { /* wirklich löschen */ }
});
// dlg.show() = nicht-modal, dlg.close() = schliessen

Eigenschaften von JavaScript

  • Skriptsprache: wird im Browser von einer Engine (V8, SpiderMonkey, JavaScriptCore) direkt ausgeführt – kein manuelles Kompilieren.
  • Dynamisch typisiert: Variablen haben keinen festen Typ, der Wert hat einen (let x = 5; x = "Text"; geht).
  • Einfädig (single-threaded): ein Befehl nach dem anderen; Wartendes (Timer, Netzwerk) läuft über Callbacks/Promises und die Event-Loop.
  • Ereignisgesteuert: Code reagiert auf Klicks, Eingaben, Timer …
  • Multi-Paradigma: prozedural, objektorientiert (Prototypen/Klassen), funktional.
  • Gross-/Kleinschreibung zählt: name ≠ Name.

Wie läuft JS im Browser? (DOM, Window, Event-Loop)

  • Der Browser liest das HTML und baut den DOM (Document Object Model) – einen Baum aus Objekten (Elemente, Text, Attribute).
  • window = globales Objekt (Fenster/Tab); document = die Seite (Einstieg in den DOM). alert() ist eigentlich window.alert().
  • JS kann den DOM ändern → Browser zeichnet die Seite neu (kein Neuladen nötig).
  • Event-Loop: JS führt Code der Reihe nach aus; Ereignisse (Klick, Timer, Antwort vom Server) werden in eine Warteschlange gelegt und der Reihe nach abgearbeitet, sobald der Code frei ist.

Konzepte & Theorie (für Textfragen)

Begriffe, die in Prüfungen erklärt werden müssen – mit kurzen Musterformulierungen.

Modaler Dialog (Modal) – Definition, Einsatz, Interaktion, Umsetzung

  • Definition: Overlay/Fenster über der Seite, das den Rest der Seite blockiert (Hintergrund abgedunkelt, nicht klickbar), bis der Benutzer reagiert.
  • Einsatz: Bestätigung («Wirklich löschen?»), Login/Registrierung, Cookie-Hinweis, Formular ausfüllen, Bild gross anzeigen, Fehler-/Wichtige Meldungen.
  • Interaktion: Buttons («OK», «Abbrechen»), Schliessen-Kreuz «×», Escape-Taste, Klick auf den abgedunkelten Hintergrund.
  • Nicht-modal: blockiert nichts (Tooltip, Toast/Snackbar, Chat-Bubble, Dropdown).
  • alert(), confirm(), prompt() sind eingebaute modale Dialoge (blockieren das ganze Script).

Textfragen: Musterantworten zum Anpassen (je 2–3 Sätze)

  • DOM: Das Document Object Model ist die Darstellung der HTML-Seite als Baum aus Objekten (Elemente, Attribute, Text). Der Browser baut ihn beim Laden auf; JavaScript kann darüber Elemente suchen, ändern, hinzufügen und löschen, ohne die Seite neu zu laden.
  • Event / Event-Handler: Ein Event ist ein Ereignis, z.B. Klick, Tastendruck oder «Seite geladen». Mit addEventListener registriert man eine Funktion (Handler), die aufgerufen wird, sobald das Ereignis eintritt; das Event-Objekt liefert Details (target, key).
  • Callback: Eine Funktion, die einer anderen Funktion als Argument übergeben und später aufgerufen wird, z.B. beim Event, beim Timer oder für jedes Array-Element (forEach).
  • Event-Delegation: Statt an viele Kindelemente einzeln einen Listener zu hängen, wird einer am Elternelement registriert. Durch Bubbling kommt der Klick dort an; über event.target erkennt man das Kind. Vorteil: weniger Code, funktioniert auch für später hinzugefügte Elemente.
  • AJAX / fetch: Daten werden im Hintergrund vom Server geladen, ohne die Seite neu zu laden. fetch liefert ein Promise; die Antwort wird mit response.json() in ein Objekt umgewandelt und danach im DOM angezeigt.
  • JSON: Leichtgewichtiges Textformat für Daten (Schlüssel-Wert-Paare, Arrays), unabhängig von der Programmiersprache; verbreitet für den Datenaustausch zwischen Client und Server. JSON.stringify erzeugt den Text, JSON.parse das Objekt.
  • Promise / asynchron: Ein Promise steht für ein Ergebnis, das erst später vorliegt (z.B. Serverantwort). Der Code blockiert nicht; mit then bzw. await wird weitergemacht, sobald das Ergebnis da ist.
  • Validierung (Client/Server): Eingaben werden geprüft (Pflichtfeld, Format, Länge). Clientseitig (im Browser, z.B. required, pattern, JS) gibt sie schnelles Feedback; sicher ist nur die serverseitige Prüfung, weil der Client manipulierbar ist.
  • Debugging: Fehler suchen und beheben. Mit den Browser-Entwicklertools: Konsole (Fehlermeldung mit Zeile), console.log, Haltepunkte im Debugger und schrittweises Ausführen, um Variablenwerte zu prüfen.
  • Web Storage: localStorage speichert Schlüssel-Wert-Paare (nur Strings) dauerhaft im Browser, sessionStorage bis der Tab geschlossen wird; die Daten werden nicht an den Server gesendet (im Gegensatz zu Cookies).
  • Single Page Application: Eine Webanwendung, die nur eine HTML-Seite lädt und Inhalte per JavaScript austauscht (Daten per fetch); fühlt sich wie eine App an, kein Neuladen bei Navigation.
  • Framework / Library: Fertiger, wiederverwendbarer Code. Bei einer Library ruft man Funktionen auf; ein Framework gibt die Struktur vor und ruft den eigenen Code auf. Vorteil: schneller entwickeln, bewährte Lösungen.
  • Verstecken vs. Entfernen: Verstecken (display:none, hidden) macht das Element nur unsichtbar – es bleibt im DOM, Inhalt/Zustand bleiben erhalten. Entfernen (remove()) nimmt es aus dem DOM; die Information ist weg.

HTTP, REST, AJAX

  • Client (Browser) sendet einen Request, der Server antwortet mit einer Response (Statuscode + Daten).
  • Methoden: GET lesen · POST neu anlegen/senden · PUT/PATCH ändern · DELETE löschen.
  • Statuscodes: 200 OK · 201 Created · 301/302 Weiterleitung · 400 Bad Request · 401 nicht angemeldet · 403 verboten · 404 nicht gefunden · 500 Serverfehler.
  • REST-API: Ressourcen über URLs (/users/5) + HTTP-Methoden, Daten meist als JSON (leichter als XML).
  • AJAX: Daten im Hintergrund nachladen, ohne die Seite neu zu laden (heute mit fetch).

Sicherheit im Frontend

  • XSS (Cross-Site-Scripting): fremder JS-Code gelangt über Eingaben in die Seite. Schutz: textContent statt innerHTML, Eingaben nie ungeprüft einfügen.
  • Same-Origin-Policy: JS darf standardmässig nur Ressourcen desselben Ursprungs (Protokoll + Domain + Port) lesen; CORS erlaubt Ausnahmen (Server sendet Header).
  • Validierung im Client ist Komfort (schnelles Feedback), keine Sicherheit – der Server muss immer nochmals prüfen.
  • Keine Passwörter/API-Schlüssel im JS-Code oder in localStorage.

Responsive Design & Barrierefreiheit

  • Responsive: Seite passt sich der Bildschirmgrösse an: <meta name="viewport" content="width=device-width, initial-scale=1">, Media Queries, Flexbox/Grid, relative Einheiten (%, rem).
  • Mobile-first: zuerst für kleine Bildschirme gestalten, dann mit @media (min-width: …) erweitern.
  • Barrierefreiheit (a11y): alt-Text bei Bildern, <label for> bei Feldern, semantische Tags (header nav main footer), genügend Kontrast, Bedienung per Tastatur, ARIA-Attribute wo nötig.

Architektur & Werkzeuge

  • Separation of Concerns: Struktur (HTML), Design (CSS), Verhalten (JS) in getrennten Dateien – darum kein Inline-JS/-CSS.
  • Library (z.B. jQuery: du rufst sie auf) vs. Framework (z.B. Angular, Vue: es gibt die Struktur vor; React ist streng genommen eine Library).
  • SPA (Single Page Application): eine HTML-Seite, Inhalte werden per JS ausgetauscht (schnell, app-artig). MPA: jede Ansicht = eigene Seite vom Server.
  • npm: Paketmanager für JS-Bibliotheken; Bundler/Build-Tools (Vite, webpack) bündeln und verkleinern (Minify) den Code.
  • Git: Versionsverwaltung (commit, push, pull, branch).

Daten von einer API laden & anzeigen

async function laden() {
  const ul = document.querySelector("#liste");
  ul.textContent = "Lade …";
  try {
    const res = await fetch("https://jsonplaceholder.typicode.com/users");
    if (!res.ok) throw new Error("HTTP " + res.status);
    const users = await res.json();                   // Array von Objekten
    ul.innerHTML = "";
    users.forEach(u => {
      const li = document.createElement("li");
      li.textContent = `${u.name} (${u.email})`;
      ul.appendChild(li);
    });
  } catch (err) {
    ul.textContent = "Fehler: " + err.message;
  }
}
document.querySelector("#laden").addEventListener("click", laden);

// Mischen (Fisher–Yates)
function mischen(arr) {
  const a = [...arr];
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}
